# Fidelity review packets

math0 formalizes the OEIS conjectures of its frontier track itself, so whether each Lean statement says what the OEIS author meant is a judgement, not a machine check. Each statement was reviewed by an agent before it was frozen. These packets come from a second, adversarial pass (29 Oct 2026) over all 110 statements, written so that people can check them in batches of ten. They are not a human review. The Lean excerpts were copied by the agent and may abridge long definitions; the linked frozen file is authoritative, and its hash is listed in [`FROZEN.sha256`](../../lean/Math0/Statements/FROZEN.sha256).

**Outcome of the pass:** 72 faithful, 38 faithful with notes, 0 questionable, 0 unfaithful; 0 major and 15 minor points.

## Minor points, to look at first

- [A090905](packet-02.md) (minor): The Lean triangle requires each row to be at least as long as the previous row (k ≥ len n). This bound comes from De Vlieger's 2016 Mathematica program. Murthy's name of the sequence ("every row product is a multiple of the previous") does not state it; the unbounded variant is A381901. The bound turns out not to matter. Rows 1..28 are identical with or without it. Moreover, once the proved statement holds, the largest prime B_n of row n forces the next row to have length at least 2B_n - 2B_{n-1}, and that is ≥ len(n) = 2B_{n-1} - 2B_{n-2}. I checked this inequality for all Bertrand primes up to index 38, and it follows from Nagura beyond that. So the bound is never binding, and the two triangles coincide for every n.
- [A093726](packet-02.md) (minor): The truth value depends on which reading of a(n) is used. The name says 'numerator of the imaginary part of the convergents'. Lean uses Im(Numerator(c_n)) = lcm(den Re, den Im)·Im(c_n), as in the program Im[Numerator[...]]. I checked numerically that the two readings first differ at n = 42 (then at 84 and 126). Under the literal-name reading the conjectured identity is false at n = 42: reduced num Im(c_42) = 18854485653829, while d·Im(c_42) = 245108313499777, with d = A093727(42) = 329919304636610. The Lean reading is the defensible one. It is the reading of the program, of He's own examples written as (A093725(n)+a(n)*i)/A093727(n), and of the only sense in which a(n)/A093727(n) is a natural quantity (Im c_n). A reviewer should still know that the alternative reading would give a counterexample rather than a proof.
- [A175385](packet-04.md) (minor): The data check pins only the numerators of S(n), not the denominators (A175386), and the conjecture is a statement about the denominator being 1. This does not affect fidelity, because S is a literal, non-truncating transcription of the sum, and I confirmed the denominators match A175386 for n = 1..25.
- [A188474](packet-05.md) (minor): The index is deliberately shifted from the literal "A137398(n+1)" to A137398(n+2). The reason is that A137398's offset was corrected in 2021: the old offset was 0, and the current one is 1. The listed numbers fix the shift unambiguously, since the row sums 1,2,7,22,74 are A137398's terms from the second on. The literal reading in today's offset is false at n = 0 (1 ≠ 0). This is the intended reading, but the Lean text departs from the verbatim OEIS text, so a reviewer should confirm it.
- [A215010](packet-05.md) (minor): 'Simple convex polygon with equal interior angles' is encoded through the edge-vector characterization: positive sides, sum of s_k * zeta^k = 0, zeta = exp(2*pi*i/N), N >= 3. It is not encoded as a geometric definition. The refutation needs only the direction 'predicate implies a genuine polygon', and that direction holds: positive sides whose direction turns by 2*pi/N at each vertex, with total turning 2*pi, form a strictly convex simple polygon with every interior angle (N-2)*pi/N. The data check validates the predicate only at N = 6. I numerically confirmed the decagon witness (1,4,5,8,9,2,3,6,7,10) used by the result: |sum| ~ 5e-15.
- [A281000](packet-06.md) (minor): Conjecture (2) is not well defined as written: A103365 has offset 1, so the k = 0 term uses A103365(0). With only the shift A103365(k) -> A103365(k+1) it is false at n = 1 (sum 3 + 3 = 6; I recomputed this). The file instead reads (-1)^k·A103365(k) as A103365(k+1), which equals (-1)^k·|A103365(k+1)|. This is an editorial correction, not the literal text. It does not change the strength of the statement: in this reading (2) is the k = 0 column of T·T^{-1} = I, so it follows from conj3. The other plausible true readings, such as Σ T(n,k)(2k+1)Cat(k)·b(n+1-k) = 0^n (row 0 of U·T), also follow from conj3. The conjunction is therefore equivalent to (1) ∧ (3), which are transcribed faithfully.
- [A308121](packet-07.md) (minor): Reading choice on the range: the OEIS text says 'If n is odd', which includes n = 1, but the Lean statement requires 1 < n. At n = 1 the literal claim fails under any reading: row 1 = [0] has odd length and no halves, and row 2 = [1] is not a rearrangement of [0]. For odd n ≥ 3, φ(n) is even, so the halves are well defined. The file documents this exclusion, and it is the only reading under which the conjecture is meaningful. Still, the result settles the conjecture for odd n > 1 and not the literal 'all odd n' wording, which is (trivially) false at n = 1. A reviewer should accept this reading explicitly.
- [A357216](packet-10.md) (minor): The kernel data check validates the computable T, not the geometric `regions` and `HasNonSimpleIntersection` that `statement` actually uses, and T = regions is not proved. A mistake in the topological encoding would not be caught by a_data. By reading, the encoding is literal and sound: open convex hull minus closed segments, Nat.card of the connected components, and k = 0 gives 1. Distinct chord indices give distinct, non-collinear segments, because a line meets the convex boundary in only 2 points. Also, the proved equality regions n k = n k^2 + 1 rules out a degenerate definition for n = 5 and n ≥ 7.
- [A362086](packet-10.md) (minor): 'Except for 9' is encoded as exempting every n with a n = 9. On a strict reading, the author is excepting the single term a(5) = 9. The Lean statement is therefore formally weaker by the claim 'the value 9 occurs only once', since a second 9 would refute the strict reading but not the Lean statement. The gap does not matter in practice. Exact computation shows 9 occurs only at n = 5 for 3 ≤ n < 1200. Using the closed form a(n) = N/gcd(N, 3(n-1)(n-3)!) with N = n^2+n-3 (which I checked against exact evaluation for n < 400), 9 | a(n) needs v_3(N) ≥ 3 + v_3((n-3)!), which is impossible for n ≥ 15 or so. The index reading (n = 9) is untenable, because a(5) = 9 is not prime.
- [A363482](packet-10.md) (minor): 'Except for 49' is encoded as exempting every n with a n = 49. On a strict reading, the author is excepting the single term a(6) = 49, so the Lean statement is weaker by 'the value 49 occurs only once'. The gap does not matter in practice. Exact computation shows 49 occurs only at n = 6 for 3 ≤ n < 1200. Using the closed form a(n) = N/gcd(N, 5(n-1)(n-3)!) with N = n^2+3n-5 (which I checked for n < 400), 49 | a(n) needs v_7(N) ≥ 2 + v_7(5(n-1)(n-3)!), which fails for all n beyond about 50 because of size. The catalog summary itself states that 49 occurs only at n = 6.
- [A363609](packet-10.md) (minor): Faces that face an enclosed cavity count as visible. The file justifies this by the listed a(26) = 93: under the other reading, the 3×3×3 cube minus its centre would give ≤ 90. But Donahoe's dice.py only searches box-plus-slab layouts and never builds a cavity, so the data are weak evidence either way. The Lean reading matches the author's convention that every exposed face counts, bottom faces included (a(1) = 21), so it is the natural one. Under the other reading, the Lean result gives only a(k^3) ≤ 6k(k+2), not equality. The projection-type lower bound plausibly also holds there, but that is not part of this statement.
- [A367119](packet-10.md) (minor): The kernel data check is on the computable surrogate `a`, which is not linked to `edges`. So the geometric statement's definitions (vertices, adjacency, placement, general position) are validated only by inspection and by my numerical check, not by a kernel-checked term. On inspection they are correct: chords cannot overlap; side pieces overlapping on a common side are excluded from the vertices by the `s ∩ t = {z}` clause; consecutive boundary points give the 3n+3 side edges; and n = 0 gives 3.
- [A386538](packet-11.md) (minor): Several listed terms from a(13) on are smaller than the true maximum area. The author's Maple/Mathematica program, 4n + 4*Sum floor(sqrt(n^2-x^2)) - 2*#distinct y, is not the convex-hull area for n >= 13; for example it gives 512 at n = 13, where the 20-gon on the circle has area 516. The Lean follows the entry's name (the maximum), not the program. This does not affect the result: the counterexample is at n = 7, where the listed a(7) = 138 equals the true maximum. I recomputed exactly that the center-0 hull has area 138 and that the hull for center (5/12, 5/24) has area 281/2.
- [A394981](packet-11.md) (minor): The literal conjecture ('if n is odd') includes n = 1, but the entry's corrected data give a(2) = 1 ≠ 4 = 4·a(1). The statement restricts to odd n ≥ 3, and literal_fails_at_one kernel-checks the failure at n = 1. This is a deliberate weakening of the literal text, needed because the literal text is false at its first instance. It is the evident intent: the pattern holds for every listed pair n = 3, ..., 19. A reviewer should accept that n = 1 is a degenerate exception (1-row rectangles, after the May 2026 data correction) and not part of what the author meant.
- [A395454](packet-11.md) (minor): Index shift: the statement does not take 'row n' in the entry's offset-0 numbering. Read that way the recurrence is false at n = 2, since the RHS is 0 (P_1 = 0) while P_2 = 2t, and it fails at every n tested. The frozen statement uses P(n) := row n-1, i.e. rows counted from 1. Of the readings I checked, this is the only nearby one that makes the formula true; reversing the row polynomials or dividing by t both fail at once. It almost certainly reflects the author's 1-based row indexing. Still, it is an interpretive reindexing, not the literal text, and a human reviewer should approve it. The proof settles the shifted claim, which is the only meaningful version.
